Clase 7 — Refactoring, Gestión de Cambios y Concepto de Versión

📅 10/10 — Docente: [Nombre]

“Cambiar sin romper, evolucionar con control”

1) Encaje curricular

En la Clase 6 aprendimos a expresar valor mediante user stories, criterios de aceptación (CA) y NFRs (atributos de calidad), además de reglas de entrada/salida (DoR/DoD).

Esa base permite que hoy abordemos cómo cambiar el software sin comprometer su estabilidad: refactoring (mejorar diseño sin alterar comportamiento), gestión de cambios (gobernar el riesgo y asegurar trazabilidad) y versionado (comunicar claramente el impacto al consumidor).

En la Clase 8 haremos esto operativo con Git: ramas, PRs, tags y releases.

2) ¿Qué es Refactoring? (definición y propósito)

Refactoring es el proceso de modificar la estructura interna del código para mejorar diseño, legibilidad y mantenibilidad, sin cambiar el comportamiento observable (los tests deben seguir pasando igual).

Beneficios: menor deuda técnica, reducción del costo de cambio, onboarding más rápido y menos defectos en evoluciones futuras.

Un refactor bien hecho aclara la intención del código y desacopla componentes para que nuevas funcionalidades sean más fáciles y seguras de añadir.

3) Code Smells (síntomas que disparan el refactor)

Un code smell no es un bug, pero indica un diseño débil que dificulta el cambio.

Ejemplos: Duplicación de código; Métodos o clases largas/Dios; Nombres ambiguos; Feature Envy; Data Clumps.

Los smells orientan qué técnica aplicar; ignorarlos hace que el sistema se rigidice con el tiempo.

4) Técnicas de Refactor

Extract/Inline Method: separar o unificar lógica para métodos más cortos y claros.

Rename: nombres que expresen propósito.

Introduce Parameter Object: agrupar parámetros para reducir firmas y expresar invariantes.

Replace Conditional with Polymorphism: estrategias para múltiples variantes por tipo.

Move Method/Field: llevar la lógica donde residen los datos.

Encapsulate Collection: exponer operaciones controladas.

Toda técnica se valida con tests antes y después.

5) Refactor Seguro

Caracterizar el comportamiento actual con tests.

Trabajar en pasos pequeños, con commits atómicos y mensajes claros.

Abrir PRs con objetivo, alcance y riesgos.

Mantener CI en verde e integrar frecuentemente.

Usar feature flags cuando el refactor toca comportamiento visible.

6) Deuda Técnica

La deuda técnica es el interés que pagamos por decisiones técnicas apresuradas o diseños improvisados.

No toda deuda es mala: a veces permite validar un mercado, pero debe hacerse explícita y tener plan de pago.

Indicadores: alta fricción para modificar un módulo, defectos repetidos, velocidad decreciente del equipo.

7) Gestión de Cambios

Proceso formal para solicitar, evaluar, implementar, validar y documentar modificaciones con control de riesgo.

Asegura trazabilidad, alineación con negocio y operación confiable.

8) Ciclo Operativo del Cambio

1) Solicitud con valor, contexto y CA/NFRs.

2) Análisis de impacto.

3) Plan: tareas, responsables, migraciones, pruebas y rollback.

4) Implementación: ramas controladas, CI/CD, revisiones y pruebas.

5) Validación.

6) Release + monitoreo.

7) Changelog y documentación.

9) Migraciones de Base de Datos

Versionar migraciones y hacerlas idempotentes.

Estrategia expand → migrate → contract.

Scripts reversibles y pruebas en staging.

10) Pruebas que habilitan el cambio

Caracterización, unitarias, integración/contrato, end-to-end y NFRs.

La cobertura de líneas ayuda, pero no sustituye pensar qué puede romperse.

11) Release y Rollback

Feature flags, canary, blue-green y rollback documentado.

12) Concepto de Versión

Una versión identifica un estado liberado del producto y comunica qué cambió, cuándo y qué tan seguro es adoptarlo.

13) Semantic Versioning

MAJOR.MINOR.PATCH

MAJOR: cambios incompatibles. MINOR: nuevas funcionalidades compatibles. PATCH: correcciones compatibles.

14) Changelog Útil

Mantener CHANGELOG.md con Added, Changed, Fixed, Deprecated, Removed y Security.

15) Métricas de Cambio

Lead Time for Changes, Change Failure Rate, MTTR y Defect Density.

16) Anti-patrones

Big Bang Refactor, refactor sin tests, romper compatibilidad silenciosa, migraciones sin rollback y releases a ciegas.
